## 四、工程与性能优化

本节围绕 PRD §6.1 四项硬指标展开：**并发≥50 QPS、AI回答≤3s 首字、API≤500ms P95、SSE 流式输出（PRD A03）**。全部方案基于已盘点数据设计（28部法规、199章、2087条、正文约30.4万字、条均134.6字、最长907字、172处内容内"第X条"交叉引用），不做选项罗列，给出明确取舍与理由。

### 4.1 硬指标分解与总体架构

| 指标 | 指标含义 | 实现手段（见节） |
|---|---|---|
| ≤3s 首字 | 用户发问到收到第一个字符（引用块或正文增量） | 检索与生成解耦、引用先返、检索并行化（4.2/4.6） |
| ≤500ms P95 | **检索链路 API**（预处理+检索+重排+引用组装，不含LLM生成）P95 | 小语料全内存检索、异步并行、连接池（4.2/4.5） |
| ≥50 QPS | 系统整体吞吐，含SSE长连接在途 | 异步IO+限流+多级缓存降载（4.4/4.5） |
| SSE流式 | 正文逐token推送 | StreamingResponse + 事件协议（4.6） |

总体架构分层：

```
[Nginx 网关] → [FastAPI 业务后端（含 rag 模块，SSE）]
                      ├─ 多级缓存(Redis/内存)
                      ├─ 检索层: Milvus(向量) + jieba-BM25(全文)
                      ├─ 重排: bge-reranker-base
                      ├─ 生成: 国内LLM API(SSE)
                      └─ 内容安全中间件: 敏感词预检/后置审核
```

说明：500ms P95 指标不把 LLM 首字计入——生成侧走 SSE 流式、耗时弹性大（受供应商排队影响），若把生成算进 500ms 无法稳定达成；故将其定为**检索链路 API 指标**，与 3s 首字指标在时间线上前后衔接（检索约 350ms 内完成，随后立即推引用块，LLM 首字在 1~2.5s 到达）。

### 4.2 RAG 全链路与首字≤3s 耗时预算

**链路时序（含预算）：**

```
用户发问
 ├─① 网关鉴权 + 敏感词预检(入口)           30~50ms
 ├─② 会话上下文组装 + 问题改写(轻量规则)    20~50ms
 ├─③ 并行检索
 │    ├─ 向量: query embedding + Milvus top20   60~90ms
 │    └─ BM25: jieba 分词 + 倒排 top20           10~20ms
 ├─④ RRF 融合 + 去重 + 相关度阈值过滤          <10ms
 ├─⑤ bge-reranker-base 重排 top10             40~80ms
 ├─⑥ 命中缓存? 是→直接复用                     <5ms
 ├─⑦ 引用块(来源/doc_no/条款) 组装并**先行推流**  累计 250~400ms  ✅ 首字=引用块
 └─⑧ LLM API 首字(TTFT)                      800~2000ms  ✅ 首字≤3s 达成
       ——正文经 SSE 逐 token 推送——
```

**关键设计——引用先于正文**：引用块来自检索+重排结果，与 LLM 生成**解耦**，无需等生成完成即可推送。做法：prompt 强制模型只能引用给定片段并标注编号 `[1][2]`，模型生成的编号与检索返回的片段一一对应。这样前端约 400ms 即看到"依据《XX条例》第X条"的引用卡片，3s 内必然开始刷正文，且因模型被约束"只许引用、不许自造"，同时服务了 PRD A01 的来源引用与避免幻觉要求。

**分块策略（与实测数据绑定）**：以**条款为最小检索单元**，2087 条即 2087 个 chunk。理由：条均 134.6 字、最长 907 字，绝大多数落在 embedding 与重排的友好长度区间，无需跨条拼接、不引入切分噪声；每条携带元数据 `doc_no / category / chapter / article_no / source`。172 处内容内"第X条"交叉引用构建**条文引用图**：检索命中某条时，若该条正文引用了他条（如四川条例引用《安全生产法》第X条），自动将被引条款追加为上下文——这同时解决了数据质量中"层级交叉引用"问题的正向利用。

**如何保证 3s 内**：检索侧预算上限 400ms（全内存或单机 Milvus 数据量 <1MB 向量，轻松达标）；LLM 侧用 `max_tokens` 限制单轮 800 以内、温度固定，并选择 TTFT 快的模型（见 4.7）。

### 4.3 向量库选型与迁移路径

| 阶段 | 选型 | 决策理由 |
|---|---|---|
| 开发期 | **Chroma（持久化）** | 单机嵌入式、零运维，向量仅 ~2087 条（千级），毫秒级返回；与 jieba-BM25 混合检索已在实训环境验证可用（见《RAG混合检索方案》）；便于快速迭代切分/元数据/过滤策略 |
| 生产期 | **Milvus Standalone（向量）+ 独立 jieba 倒排（BM25）** | 2087 条虽小，但 50 QPS + SSE 长连接要求稳定吞吐与并发读，Chroma 受 Python GIL 与本地计算限制不适合承载线上；Milvus 支持标量过滤（可按 doc_no/category 预过滤）、连接池、水平扩容；BM25 数据量小，jieba 分词倒排一次载入内存即可 |

> 若集团已有 Elasticsearch 8.x 集群，可复用它做生产向量库（自带 HNSW kNN 与 BM25），无需引入 Milvus——但决策上以**Milvus 为缺省**，理由：避免与集团既有业务索引抢资源，向量检索隔离部署、故障域清晰。

**迁移路径（四步，全量迁移约 1 分钟内完成）：**

1. **接口抽象**：定义 `VectorStore` 接口（`search(query_vec, top_k, filter)` / `insert()` / `delete()`），Chroma 与 Milvus 各实现一份，业务代码不感知底层。
2. **数据导出**：脚本将 Chroma collection 导出为 `chunks.jsonl`（`id / vector / text / metadata`），写入 `export/` 目录留档。
3. **批量导入**：用 `pymilvus` 客户端分 4 批（每批 ~520 条，2.5 节批量 embedding 复用同一份向量，无需重算）插入 Milvus，Schema 与接口保持字段一致。
4. **灰度切换**：先只读切 Milvus，跑一周检索回归（top10 命中对比 Chroma 结果一致性），稳定后下掉 Chroma 实例。

### 4.4 缓存策略（多级缓存）

数据量小、查询模式高度集中（培训问答高频重复），缓存收益显著，是省成本、扛 QPS 的第一杠杆。

| 层级 | 载体 | 缓存内容 | 命中条件 | TTL | 价值 |
|---|---|---|---|---|---|
| L1 检索结果缓存 | 进程内 LRU（rag-service） | 归一化 query → top10 片段ID+分数 | 归一化后文本完全相同 | 5min | 省 embedding+检索 |
| L2 语义近似缓存 | Redis | query embedding → top10 片段ID | 向量余弦 ≥0.95 视为同问题 | 10min | 同义改写的重复问题直接命中 |
| L3 生成结果缓存 | Redis | 规范化 query → 完整 SSE 事件流 | L2 命中且时间窗内 | 30min | **不调 LLM**，最大降本 |
| L4 热门知识点缓存 | 内存+Redis | 高频知识点 → 预聚合片段集 | 统计出的 top50 热门词命中 | 1h | 热门问答零检索 |

**Key 设计**：query 先做轻量归一化（去标点/停用词、统一"安全生产法"与"《安全生产法》"等别名），再取 embedding 做相似度判定——同一问题的不同问法（"有限空间作业要求""有限空间作业有哪些规定"）在 L2 命中，直接复用 L3 的生成结果，返回完整 SSE。

**防穿透/防击穿**：L2/L3 对"无答案"的 query 也缓存空结果（TTL 缩短为 60s），防止每次穿透到 LLM；缓存更新用互斥锁+单飞（single-flight），同 key 并发只放行一个回源。

### 4.5 并发与限流（支撑 50 QPS）

**并发预算**：50 QPS × 平均响应 2.5s ≈ **125 个在途请求**。检索侧（350ms 内完成）瞬间释放，真正的长连接只占 LLM 流式阶段，故瓶颈不在检索而在 LLM 供应商并发。

**手段：**

1. **检索全异步化**：rag-service 基于 FastAPI async；query embedding（aiohttp 调供应商 embedding API）与 BM25、向量检索三者 `asyncio.gather` 并行，互不等待。
2. **连接池**：embedding API 用 `aiohttp.TCPConnector(limit=100, ttl_dns_cache=300)`；Milvus 用连接池（单实例 200 连接）；Redis 用连接池（50）。
3. **LLM 并发控制与熔断**：对生成侧设并发信号量（Semaphore，按供应商配额设 8~16），超出则排队；连续 5 次超时/429 触发熔断（退避 30s），保障 50 QPS 下不把供应商打挂、也不互相拖累。
4. **限流**：Nginx 按用户 `limit_req`（如 10 req/s/用户），rag-service 内再按 IP+token 做滑动窗口兜底；DDoS 级别由网关承接。
5. **批量 embedding（建库侧）**：2087 条款分批，`batch=32` 一次请求嵌入，总调用约 66 次，避免逐条请求；在线 query embedding 单条走连接池。

### 4.6 SSE 流式输出与引用先返

**协议设计**（`text/event-stream`，UTF-8，`X-Accel-Buffering: no` 关掉代理缓冲）：

```
-- event 1: meta（约 400ms 到达，首字）
event: meta
data: {"task_id":"...","citations":[{"index":1,"doc_no":"...","title":"四川省...条例",
       "article_no":"第十条","snippet":"..."}, ...]}

-- event 2..n: 正文增量
event: delta
data: {"d":"生成文本增量token"}

-- event 3: 结束
event: done
data: {"full_text":"...","source_ids":[...]}
```

**要点：**
- **引用先返的实现**：citations 在 4.2 步⑦已组装完成，不等 LLM；前端收到 `meta` 即渲染"依据来源"卡片并高亮条文号，正文到达时对应位置插入 `[1][2]` 锚点。
- **防幻觉钩子**：prompt 明确"仅允许引用给定片段、编号必须来自 citations 列表"，重排后片段本身附带 doc_no+article_no，溯源天然成立。
- **断连处理**：任务队列化，`task_id` 支持断线重连续推；`done` 前发送心跳 `event: ping` 保活（60s）。
- **异常分支**：检索为空时直接返回 `meta`（空引用）+ `delta`（"知识库未检索到相关内容，已转人工"），不调用 LLM，杜绝幻觉兜底回答。

### 4.7 成本优化

**模型选型（按量计费，明确首选小模型）：**

| 环节 | 选型 | 理由 |
|---|---|---|
| 生成 | **文心 ERNIE-Speed 或 通义 qwen-turbo 级别小模型** | TTFT 快（利于 3s 指标）、单价低；本场景是"强检索+小模型"——2087 条规范条文检索足够精准，答案多为引用+要点复述，不需要强推理大模型 |
| 复杂问题路由 | 命中"多条款交叉/事故定责/跨法比较"等意图时，才路由到 ERNIE-4.0-Speed/qwen-plus | 兜底少量高难问题，控制成本占比 |
| 重排 | bge-reranker-base 本地部署 | 不按调用计费，CPU/GPU 均可用，40~80ms |
| embedding | bge-large-zh 本地部署 | 不按调用计费，且 2087 条建库仅需一次批量计算 |

**Prompt token 精简（约省 40%~60%）：**
- 系统提示词固定模板化并做版本号，不随问答拼接；正文 prompt 仅携带 top10 命中片段（每条≤907字，多数字段远低于此），命中段先截断至 300 字再拼入；
- 问题改写用规则而非再调模型；多轮历史只带最近 2 轮且截断；
- 目标单轮 token ≈ 系统 150 + 上下文 ~2000 + 输出 ≤800 ≈ **3k token/问**，按小模型单价估算单问成本 <0.01 元；L3 生成缓存命中时成本为 0。

**embedding 建库批处理**：建库一次性批量（batch=32），后续**增量入库走定时任务**（每日扫描数据资产目录 diff，新/变条文单独嵌入，复用原接口）；全量重算仅版本升级时触发。

### 4.8 部署与 SSE 流式对接（全 FastAPI 同栈）

**容器化：**
- rag-service 打 Docker 镜像：`python:3.10-slim` 基础镜像 → 分层（requirements 层 + 代码层 + 模型缓存层）；jieba 词典、bge 模型、敏感词库以挂载卷或镜像内置方式提供；
- 环境配置走 `.env`（每环境一份，遵循实训约定），密钥（LLM API key、Redis/Milvus 密码）不落镜像、由部署平台注入；
- 组件清单：`rag-service`（FastAPI，1 副本起步，可扩 2~4）、`milvus`（standalone）、`redis`（缓存）、`milvus-etcd/minio` 依赖。总资源预估：CPU 8 核 / 内存 16G 可支撑 50 QPS。

**SSE 流式对接（全 FastAPI 同栈，无跨语言桥，对齐 PRD §2 与 ARCHITECTURE §3.1）：**

| 方案 | 方式 | 取舍 |
|---|---|---|
| **A（推荐）** | `/api/chat` 由 FastAPI 后端接收，**进程内调用 rag 模块**，`StreamingResponse` 逐事件 `yield`（meta→delta→done）回前端 | 后端统一鉴权/权限/日志，SSE 原生无转发，部署最简单，前端只对接一套 API |
| B | rag 部分独立部署为另一台 FastAPI 服务，后端内用 `httpx` 流式转发 SSE | 便于 rag 独立扩缩容，多一跳内网转发（延迟极小），仍是同一 Python 栈 |

SSE 与 Nginx 注意：`proxy_buffering off`、`proxy_read_timeout 120s`、`http/1.1` 长连接。

**观测**：Prometheus 暴露指标——`first_token_ms`（首字）、`retrieval_p95`、`cache_hit_rate`（L1~L4）、`llm_qps`、`fail_rate`；告警阈值：首字 >3s、检索 P95 >500ms、LLM 熔断触发。

### 4.9 敏感词过滤与内容安全接入位置

接入**三个位置**，前置拦截 + 后置审核双保险：

1. **入口（FastAPI 中间件/网关层）**：用户提问先过敏感词预检（本地 DFA 词典 + 可选云内容安全 API 同步扫描），命中即返回拒绝，**不进入检索与 LLM**，省资源也防诱导注入。
2. **LLM 输出（流式过程中）**：`delta` 增量逐片过内容安全（国内供应商 API 自带输出审核 + 本地敏感词库双检），违规片拦截为 `[已屏蔽]` 并追加事件；流式下审核粒度以句为单位，避免整段缓存延迟。
3. **落库前**：问答日志（含 prompt/回复）写入审计库前再扫一遍，防止通过检索片段间接携带敏感信息入库。

敏感词库随法规数据资产目录一并维护（data/sensitive_words.txt），增量上线走与法规一样的每日 diff 流程。

---

以上方案相互咬合：检索 350ms 内完成并先行推送引用块（同时满足首字≤3s 与 500ms P95）；2087 条/条均 134.6 字的数据形态决定"以条为 chunk + 全内存检索 + 多级缓存"是成本与性能的最优解；生产向量库选 Milvus、开发期 Chroma，接口抽象保证迁移零业务改动；小模型 + 强检索 + 缓存三级配合，把单问成本压到 0.01 元以内并稳定扛住 50 QPS。
