## 知识库构建

本节覆盖 RAG 上游的语料组织与知识库构建：承接已实测的数据资产（28部法规、199章、2087条、全文303734字、条均134.6字、正文172处"第X条"内容引用），把盘点结果落成结构化、可溯源、可增量、可扩展的检索底座，直接支撑 A01 的精准检索与 A01 的来源引用，并为模块三出题提供干净的"知识点-答案-解析"来源。

### 2.1 总体架构：三层语料，单一知识底座

**决策**：开发期用 Chroma 单 collection（`shudao_kb`），生产期迁移 Milvus 时同 schema 平移；不按层级拆多个向量库。理由：2087 条的规模远未到分片量级，单一 collection + 元数据过滤可以避免多库检索后的融合复杂度，且后续企业文档补充只需往同一库追加。

### 2.2 法规语料组织与检索优先级

#### 2.2.1 效力分层与冲突裁决

**决策**：元数据记录 `region` + `doc_level`（数值），检索阶段**不删结果**，裁决放在排序与作答阶段。裁决规则写入 Prompt，并在代码层做兜底排序：

1. 法律 > 行政法规 > 部门规章；法律 > 地方性法规 > 政府规章；
2. 同位阶：新法优于旧法；特别规定优于一般规定；
3. 部门规章与地方性法规同位阶冲突时，在四川地域内适用四川本地规定。

#### 2.2.2 检索优先级：四川法优先、国家法兜底

**决策**：主召回不做层级过滤（保 recall），排序时用 `region`/`doc_level` 加权；四川法召回不足时，自动补召国家法同主题条款。这样"有限空间作业""高速公路施工安全"等四川本地高频场景优先命中 11 部主体法规，涉及上位依据（如处罚、事故报告）时国家法自然浮现。

#### 2.2.3 跨法规交叉引用（172 处）的处理

实测正文含 172 处"第X条"式内容引用（全文"第X条"字面共 2259 处，含 2087 个条号头），典型如四川条例"依照《中华人民共和国安全生产法》第X条"。**决策：原文保留 + 引用展开双机制，不改写正文**：

1. **原文保留**：`content` 一字不改，被引条款仍独立存在于其所属 doc 的块中，不破坏引用地址，杜绝改写引入的幻觉。
2. **引用索引**：全量扫描 172 处，用正则 `《[^》]{1,30}》第[一二三四五六七八九十百零]+条` + 指代映射表（"本法/该条例"解析到当前 doc）建引用边，写入元数据 `ref_out`。
3. **检索时引用展开**：命中条含 `ref_out` 时，自动把被引目标条（在库内者）一并召回进上下文。解决"四川条例引用国家法、但国家法条文未被召回"的检索断层，让回答能同时给出上位依据原文。
4. 被引目标在库外的（引用已废止旧版或外部文件）：保留引用文本，`ref_out` 标记为"库外/待补"，进入企业补充清单。

### 2.3 分块策略：章/条原子分块 + 父子块

#### 2.3.1 决策：每"条"一块（原子分块），章头为辅助块

**为什么优于定长切块**（以 200 字/50 重叠对比）：

| 维度 | 定长切块 | 按条原子块（选定） |
|---|---|---|
| 引用完整性 | "第X条"编号常被腰斩或并进相邻块 | 一条=一块，引用地址天然成立 |
| 问答粒度 | 一块常横跨 1-2 条边界（条均仅 134.6 字），答案边界模糊 | 与"依据第X条"的提问粒度精确对齐 |
| 交叉引用 | 172 处"第X条"引用无法稳定定位到块 | 每条有稳定 ID，引用展开可落地 |
| 冗余 | 重叠产生重复存储与召回噪声 | 无重叠 |
| 更新 | 修订一条牵动多个块 | 按条精准替换（见 2.5.2） |

条均 134.6 字（15–907），绝大多数条一次嵌入即可高质量向量化（bge-large-zh max_len 512 token 余量充足），**完全不需要为"对齐长度"而切**；而定长切块恰恰在均匀化条的结构。规模对比：定长约 2025 块（303734/(200-50)），原子分块 2087 条 + 199 个章头/序言辅助块 ≈ **2286 个父块**，块数同量级，但结构质量天差地别——原子块换来的是"引用可溯源、更新可定位"。

章头辅助块用于给章的语境（"本章适用范围"类信息），同时作为 A01 来源引用的章级来源。

#### 2.3.2 长条二次分块：父子块保留上下文

实测最长 907 字，超 bge-large-zh 安全长度。**决策：分块阈值 400 字**（留安全余量，中文约 1.1-1.3 字/token，400 字内稳妥；907 字有超限风险）。

- `content ≤ 400 字`：单块，既是父也是唯一子（`is_parent=true`）。
- `content > 400 字`：父块 = 整条全文（**不嵌入**，仅存文本+元数据）；子块 = 按句切分（句号/分号/顿号为界，每组 100-250 字，相邻子块重叠 1 句）。
- **召回只在子块上做**（避免长条整体嵌入稀释语义，提升检索精度）；命中子块 → 返回**父块全文**给 LLM（保证回答上下文完整）。
- A01 来源引用展示**始终以父块为准**（法规名+章+第X条），子块不单独作为引用来源。

预期 >400 字的条占长尾（估计不足 10%，建议先用脚本对 2087 条实测统计后固化阈值），不影响总体块数量级。

### 2.4 块元数据 Schema

写入 Chroma metadata，同时服务"检索过滤 + A01 来源引用 + 更新定位"：

| 字段 | 类型 | 示例 | 用途 |

| chunk_id | str | `scaq_第二十四条_v2023` | 幂等 upsert / 更新定位 / 引用展示 |

| title | str | 四川省安全生产条例 | 引用展示 |
| doc_no | str | 川常备〔2023〕17号 | 引用展示 |
| category | str | 地方性法规 | 层级展示 |
| doc_level | int | 4 | 效力排序（数值，见 2.2.1） |
| region | str | 四川 / 国家 | 本地优先过滤 |
| chapter | str | 第三章 | 引用展示 |
| article_no | str | 第二十四条 | 引用展示 |
| content | str | ……（原文） | 召回返回 |

| parent_id | str | 父块 chunk_id | 子块→父块回溯 |

### 2.5 落库流程与增量更新

#### 2.5.1 全量构建流水线

```
crawler_output/*.json
  → audit.py   质量审计（输出 json 报表，见 2.7）
  → clean.py   清洗（去 BOM/空格、补元数据、规范化）
  → parse.py   解析 chapters/articles → 原子块 + 章头块
  → split.py   长条二次分块（父/子）
  → embed.py   bge-large-zh 生成向量
  → load.py    写入 Chroma（collection=shudao_kb, id=chunk_id, 幂等）
  → verify.py  抽样验证召回命中率
```

落地约定（沿用项目既定）：脚本从根目录运行；embedding 模型与向量库放仓库根；每日期文件夹一份 `.env` 配置模型路径与库连接；transformers 加载本地模型**必须用绝对路径**（相对路径报 HFValidationError），Windows 控制台先 `reconfigure(encoding='utf-8')`。

#### 2.5.2 增量与修订更新

**决策：全量重建 + 按条增量 upsert 双轨，不建额外版本库**，靠 `chunk_id` 幂等 + `version` 字段实现：

- **补漏/新法规**：文件放入 `crawler_output` → 重跑 clean/parse/embed/load，upsert 幂等，只影响新增 `doc_id`。
- **法规修订**：更新源文件 → 人工核对修订依据（政府公报/官网）→ 最新条文以含新 `version` 的 `chunk_id` 覆盖 → 检索默认过滤 `is_latest=true`。
- **旧版本处理（决策）**：不删历史，`version` + `is_latest` 标记，默认只召回现行版。2087 条规模保留历史版本开销可忽略，且为"新旧条款对比"类追问留后手。现成的例子——四川省消防条例 `status=已修改`（2011 生效）：核实最新修订文本 → 入新版 → 旧版归档。
- **生产迁移**：数据规模小，迁 Milvus 时全量重建一次即可（向量 + 标量过滤 + ID 去重）。

### 2.6 企业文档补充导入路径

现状缺口：内部制度/操作规程/事故案例无数据。**决策：Web 管理后台上传 → 解析分块 → 人工审核发布**三段式管道：

1. **上传解析**：管理员上传 Word/PDF/MD/TXT，`python-docx` / `pypdf` / `docx2txt` 解析，超长扫描件走 OCR 预案。
2. **分块**：企业文档无"条"结构，**按标题树切块**（一/二级标题为界），长章节沿用 2.3.2 父子块；无标题文档先 `jieba` 分句再按语义阈值聚合。
3. **审核发布**：预览页展示分块结果与元数据草稿 → 人工确认 `doc_type` / `access_level` / 生效日期 → 入同库（`doc_type` 区分制度/规程/案例，`access_level` 控制可见范围，检索阶段按用户权限过滤）。
4. **补充优先级建议**：先补 ① 蜀道集团安全生产责任制内部制度；② 高频工种操作规程（隧道、桥梁、高边坡、有限空间作业）；③ 近三年典型事故案例与整改报告。
5. **案例类特殊处理**：全文脱敏（人员姓名/单位），并在文首加"结论性要点"前置段落，便于检索命中与 A01 来源引用。

### 2.7 数据质量治理

#### 2.7.1 已识别问题清单（实测）

| 问题 | 实例 | 处置 |
|---|---|---|
| title 前导空格 | " 四川省生产安全事故报告和调查处理规定"、" 四川省突发事件应对办法" | `strip()` 后重建索引 |
| doc_no 为空 | 安全生产法、四川地灾条例、消防条例、道路运输条例等 15 部 | 官网核对人工补；兜底置"—" |
| effective_date 为空 | 建设工程条例、行政处罚办法、应急预案办法、事故报告条例等 6 部 | 从源网页补；兜底用 publish_date |
| status 为空/措辞不一 | 行政处罚办法 `status=""`；事故报告条例 `status="有效"` | 统一为"现行有效/已修改/已废止"三态 |
| 版本疑似过期 | 消防条例"已修改"（2011）；生产责任规定 2007、突发事件办法 2012 | 人工核实修订/废止后走 2.5.2 |
| 层级交叉引用 | 四川条例引用《安全生产法》 | 引用索引 + 展开（2.2.3） |

#### 2.7.2 清洗与校验规则（内建于 clean.py / verify.py）

1. title 统一 `strip()`；全文去 BOM、统一换行 CRLF→LF；正文 `article_no` 保留中文编号原样（引用地址用原文）。
2. 空元数据三级兜底：官网核对 → 相邻字段推导（`effective_date ← publish_date`）→ 占位符"待核实"并打 flag。
3. 校验断言：每 doc 章/条/总字符与盘点一致（199 章 / 2087 条 / 303734 字）；条号唯一且递增；`full_text` 与 `chapters` 拼接一致性校验。
4. 审计脚本沿用 `_rag_data_audit.json` 结构，增加**字段级缺失统计**，每次重建必跑并回归比对差异。

#### 2.7.3 质量闸门（建议）

以审计报表的"字段缺失率、172 处引用解析覆盖率、未补元数据清单"作为上线准入与定期巡检指标：引用解析覆盖率（成功解析到库内目标的比例）尤其重要，直接决定"四川条例引用国家法"场景的答案质量。
