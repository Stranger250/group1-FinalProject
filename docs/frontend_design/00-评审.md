# 前端设计完整性评审

> 评审对象：`docs/frontend_design/01~05` 五个章节
> 评审基准：后端 `backend/app/api/{auth,ai,chat,exam,exam_running,hazard,paper}.py` + `main.py` + 相关 schema/service（字段级逐字核对）；`docs/PRD.md §9.1`

### 1.2 反向缺口（前端依赖后端缺失）

- **F1 [高]**
  - 涉及章节：05 §4.1 + §⑥.1（阻塞）；关联 01 §6.2 菜单
  - 问题描述：05 的选卷页 P09-A 依赖公开接口 `GET /api/v1/exams/papers`（仅 PUBLISHED、脱敏、无答案），但后端 `exam_running.py` 无此路由；现有 `GET /api/v1/papers` 带 SAFETY/ADMIN 门禁且返回含答案，员工不可用。**该接口未实现前，EMPLOYEE 无法进入考试，P09-A 不可联调**。设计已自我标注，但属唯一阻塞性缺口，需优先与后端排期。
  - 修改建议：后端在 `exam_running.py` 增加 `GET /api/v1/exams/papers`（仅 PUBLISHED、脱敏字段按 05 §4.1）；或将 `GET /papers` 拆出公开脱敏变体。前端路由 `meta.menu='exam'` 的「考试成绩」入口（见 C3）与本接口共同决定考试端菜单形态，需一并定稿。

## 审计二：PRD §9.1 功能验收清单闭环检查

| §9.1 验收项 | 是否闭环 | 说明 |
| --- | --- | --- |
| 登录/注册、JWT 鉴权、角色权限、文件上传（类型/大小校验） | ✅ 闭环 | 01 §3/§4/§7 + 02 §3/§4.2/§2.5；上传双端校验、401/403 处理完整 |
| 模块一：上报（文字+图片+等级）、列表（筛选/分页/**排序**）、详情（时间线） | ⚠️ **排序未闭环** | 见 R1 |
| 模块二：智能问答（多轮）、会话管理（新建/列表/删除）、SSE 流式输出 | ✅ 闭环 | 03 §3.1~§3.3；多轮历史、中断/失败重试齐全 |
| 模块三：题库 CRUD、AI 出题、手动/智能组卷、在线考试（倒计时/自动保存/防切屏）、自动阅卷与成绩单 | ✅ 闭环 | 04 §2~§4 + 05 §③；倒计时以服务端 remaining_seconds 为权威、防切屏第 4 次自动交卷、成绩单复用交卷响应，均与后端逐字段一致 |

- **R1 [中]**
  - 涉及章节：02 §5（隐患列表）；PRD §3.2 H02 + §9.1
  - 问题描述：PRD H02 验收要求「支持按上报时间/**等级**排序」，§9.1 明确「列表（筛选/分页/**排序**）」。后端 `GET /hazards` 无 `sort`/`order_by` 参数（固定 `create_time DESC`），02 列表页也无排序控件/说明。**该验收项无论前后端都无法满足**，设计未对"排序"做任何处理或降级说明。
  - 修改建议：二选一——(a) 与后端约定增加 `sort` 参数（`create_time`/`level` + `order`），02 §5.2 请求参数表补 `sort` 字段、表格列头加排序交互；(b) 若本期明确不做，在 02 §9 联调注意中显式声明「排序不在本期」，避免验收时被挑出。

其余 E02「生成结果批量入库 / 审核通过率 ≥80% 展示」、E03「不足时提示」、E04「刷新恢复 / 切屏超限提示」、E05「多选全对得分/漏选 0 分、只展示后端已算 score」等验收细节均在 04/05 中闭环，与后端行为一致。

## 审计三：跨章节一致性

### 3.1 已核验一致（通过项）

- **token 注入**：各章统一 `Authorization: Bearer <token>`，localStorage key `shudao_token`，SSE 用 fetch 手带头（01 §4.1 / 03 §4.0 / 05 §④）。
- **401 处理**：各章一致——清登录态 → 跳 /login 带 redirect（01 §4.1 / 02 §2.1 / 03 §5 / 04 §5 / 05 §⑤）。
- **{code,message,data} 解包**：`code!==200` 视为业务失败读 `message`，各章一致。
- **等级/状态/题型/难度/试卷状态枚举**：02 的 `CRITICAL/MAJOR/GENERAL/MINOR`、`WAIT_PROCESS/FINISHED` 与 `model/hazard.py` 逐字一致；04 的 `SINGLE/MULTIPLE/JUDGE/FILL`、`EASY/MEDIUM/HARD`、`PENDING/APPROVED/REJECTED/DISABLED`、`manual/ai`、`DRAFT/PUBLISHED/DISABLED`、`[30,60,90]` 与 `schema/question.py`/`schema/paper.py` 逐字一致；05 的 `state ONGOING/SUBMITTED`、`status PASS/FAIL`、`reason manual/timeout/cheat_limit` 与 `exam_service` 逐字一致。
- **角色判断**：管理页门禁 `[2,3]`（SAFETY/ADMIN）与后端 `require_roles(RoleId.SAFETY, RoleId.ADMIN)` 口径一致（仅写法类型不一致，见 C2）。
- **AI 识别回显**：02 §4.3 完整体现——`detections[]` 多框编号、`annotated_url` 多框标注图（无有效框为 null 时隐藏）、`confidence/reason` 回显、`report` 原样回传 `risk_report`；01 §9 契约字段与 `hazard.py` 的 analyze 响应逐字段一致。✅
- **SSE meta/delta/done 契约**：01 §5 / 03 §4.1 与 `qa_service._sse` 逐字段一致——`meta{conversation_id,user_message_id,mode,confidence,citations,rewritten_used}`、`delta{text}`、`ping{type}`、`done{answer_id,citations,grounding_score,synthetic,error?}`；`mode ∈ full/conservative/refuse`（retriever `classify` 确认）；拒答路径 `done.answer_id=0`；`CiteCard` 与 `citations.py::to_source` 逐字段一致。✅
- **考试 sheet 契约**：05 §4.3 `ExamSheet`/`ResultSheet` 与 `exam_service._exam_sheet/_result_sheet` 逐字段一致（含 `remaining_seconds` 权威倒计时、`switch` 响应 `triggered:False` 恒 False、`max` 合并、`cheat>3` 触发、`Cache-Control:no-store`）。✅

### 3.2 不一致项（按严重度排序）

- **C1 [高] 四章路由定义互相冲突，无法合并成一份 router/index.ts**
  - 涉及章节：01 §3.1 vs 02 §1 vs 03 §1 vs 04 §1/§5 vs 05 §①
  - 问题描述：
    - 隐患：01 用 `/hazard/report`、`/hazard/list`、`/hazard/detail/:id`；02 用 `/hazards/report`、`/hazards`、`/hazards/:id`（前缀单复数不同、列表路径不同）。
    - AI 助手：01 用 `/ai`；02 占位 `/assistant`；03 用 `/ai/assistant`（三种路径）。
    - 考试管理端：01 用 `/exam/question-bank`、`/exam/ai-generate`、`/exam/paper`；04 用 `/exam/questions`、`/exam/ai/generate`、`/exam/ai/batches`、`/exam/ai/batches/:batchId`、`/exam/ai/stats`、`/exam/papers`、`/exam/papers/create`、`/exam/papers/:pid`（几乎完全不同）。
    - 考试端：01 用 `/exam/exam/:paperId`（作答，URL 带 paperId）、`/exam/result` + `/exam/result/:recordId`（成绩）；05 用 `/exams`（选卷）、`/exams/:recordId`（作答，URL 带 recordId）、`/exams/:recordId/result`（成绩单）。且 01 §6.2 侧栏菜单缺「考试中心/在线考试」入口，05 §①假设存在顶部导航「考试中心」菜单。
    - 05 论证了 recordId 才是刷新恢复的正确锚点（paperId 无法恢复），因此 01 的 `/exam/exam/:paperId` 方案是错的。
  - 修改建议：以 05 的考试端路由（recordId 锚点）+ 04 的管理端路由为主体，01 统一改为 `/hazards/*`、`/ai/assistant`、`/exam/...`，侧栏菜单与 05 的「考试中心」入口、成绩入口对齐；定稿一份 router/index.ts 作为唯一真源，其余章节引用而非重复定义。

- **C2 [高] `meta.roles` 取值类型冲突（数字数组 vs 字符串数组）**
  - 涉及章节：01 §3.1/§3.2 vs 04 §0/§5
  - 问题描述：01 定义 `roles?: number[]`、守卫用 `to.meta.roles.includes(userStore.user.role_id)`（role_id 为数字），且 01 路由用 `roles: [2, 3]`；04 却定义 `meta.roles: ['SAFETY','ADMIN']`（字符串），守卫写「`role_id` 为 1 或不在 `meta.roles` 则拦截」。若混用，`['SAFETY','ADMIN'].includes(2)` 恒为 false，SAFETY/ADMIN（2/3）会被守卫误拦，管理页无法进入——属实现级 bug 隐患。
  - 修改建议：全站统一 `meta.roles: number[]`（`[2,3]`），守卫统一 `!roles.includes(userStore.user.role_id)`；角色常量统一数字 `RoleId`（1/2/3），删除字符串 `'SAFETY'/'ADMIN'` 写法。04 §5 路由表与 04 §0 同步修改。

- **C3 [高] 01 菜单「考试成绩」指向的成绩列表页在后端/设计均无数据源**
  - 涉及章节：01 §3.1/§6.2 vs 05 §①
  - 问题描述：01 侧栏菜单含「考试成绩 → /exam/result」（roles: null），暗示存在"我的考试记录列表"页；但 05 只定义了单条成绩单页 `/exams/:recordId/result`，后端 `exam_running.py` 也**没有「查询当前用户考试记录列表」接口**。菜单项落地后无处取数（既无页面也无 API）。
  - 修改建议：三选一——(a) 后端新增 `GET /api/v1/exams/records`（本人历史记录列表，分页），前端补 P10 成绩列表页；(b) 删除该菜单项，成绩单仅由交卷后跳转/深链直达；(c) 菜单改为「最近一次成绩单」。需与后端排期一起定稿，避免出现死菜单。

- **C4 [中] 登录后默认落地页不一致**
  - 涉及章节：01 §3.2 vs 02 §3.2/§1
  - 问题描述：01 守卫中已登录访问 /login → `/home`，且 `/` 重定向 `/home`；02 则 `router.replace('/hazards')`、`/` 重定向 `/hazards`。用户登录后落在首页还是隐患列表不一致。
  - 修改建议：统一落地页（建议 `/hazards` 列表，业务价值更高；`/home` 作为可选聚合首页），01 §3.1 `/` redirect 与 §3.2 一并同步。

- **C5 [中] 目录/文件命名两套并存**
  - 涉及章节：01 §2 vs 02 §9 vs 04 §0.2 vs 03 §2
  - 问题描述：01 用 `src/store/`（`store/user.ts`、`store/modules/*`）+ `api/request.ts`；02/03/04 用 `src/stores/`（`stores/auth.ts`、`stores/chat.ts`）+ `api/http.ts`（02）vs `api/request.ts`（04）+ `api/question|ai|paper.ts`（04）。同一工程不能同时出现 `store/` 与 `stores/`、`request.ts` 与 `http.ts`。
  - 修改建议：以 01 为准统一目录 `src/store/` 与 `src/api/request.ts`（或单章拍板后全局改名）；axios 封装命名、store 文件名在各章节保持一致。

- **C6 [中] upload/analyze 响应解包策略冲突**
  - 涉及章节：01 §4.3 vs 02 §2.1
  - 问题描述：01 为 `/hazards/upload`、`/hazards/analyze` 单独定义 `uploadRequest`，**不做 JSON 解包**（返回原始 `ApiResponse`，理由：业务失败要拿原样 body、含 503 降级信息）；02 §2.1 只有一个 http 实例，成功拦截器统一 `code===200 → 返回 data`，上传/AI 识别同样被解包。两套语义下 analyze 调用方拿到的对象形状不同（`{code,message,data}` vs `data` 本体）。
  - 修改建议：统一为一种——推荐 01 的方案（upload/analyze 走 `uploadRequest` 返回 `ApiResponse`，调用方按 `code` 分支；普通接口走 `request` 解包），02 §2.1 补充说明并在 §7.5 analyze 契约中明确"调用方拿原始 body"。

- **C7 [中] Markdown 渲染库不一致**
  - 涉及章节：01 §1.2/§8.2 vs 03 §0/§3.8
  - 问题描述：01 依赖清单写 `markdown-it`（"净化见模块二章节"）、§8.2 再次写 "markdown-it 渲染并净化"；03 却用 `marked + DOMPurify`。同一项目只能引入一个。
  - 修改建议：以 03 为准（`marked` + `DOMPurify` 方案更成熟），01 §1.2/§8.2 改为引用 03，或全局统一为 markdown-it；`utils/markdown.ts` 归属与净化管线只定义一处。

- **C8 [低] 04 试卷时长禁改条件缺「已发布」限定**
  - 涉及章节：04 §4.2 vs `paper_service.update`
  - 问题描述：后端仅在 `status==PUBLISHED` **且**存在进行中考试时禁改 `duration`（草稿期可改）；04 §4.2 写"有进行中考试时 duration 禁改"，丢掉了 PUBLISHED 前置条件，前端禁用逻辑可能过严。
  - 修改建议：前端禁用条件同步为「已发布 且 有进行中考试」，04 文案补充。

- **C9 [低] 批量审核 body 未含 `interference_verified`**
  - 涉及章节：04 §3.2/§3.3 vs `schema/ai.py::BatchReviewIn`
  - 问题描述：后端 `BatchReviewIn` 含 `interference_verified: bool = False`，04 批量审核 body 只列 `action/review_note/ids`（不传则恒 False）。单题审核有"已核对干扰项"勾选，批量通过时无法一并勾选，行为不对称。
  - 修改建议：批量审核对话框（至少"批量通过"）补充 `interference_verified` 勾选并传入；或显式声明批量审核暂不支持并记录到 §6 待办。

- **C10 [低] 404/403 提示文案各章措辞不一**
  - 涉及章节：01 §4.2 vs 04 §5 vs 05 §⑤
  - 问题描述：01 表："404 → 请求的资源不存在"（不区分无权/不存在）、"403 → 无权限访问该接口"；04："403/404 → 无权限或资源不存在"；05："404 → 记录不存在或无权限"。语义一致但文案不统一。
  - 修改建议：抽一个常量（如 `NOT_FOUND_MSG` / `FORBIDDEN_MSG`）在 01 §4 统一导出，各章引用；顺带统一 `ElMessage` 行为。
